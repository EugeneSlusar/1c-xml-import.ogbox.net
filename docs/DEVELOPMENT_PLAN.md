# План разработки MWP

## Исходное состояние

На 27 августа 2026 года в рабочей папке была только спецификация `start_prompt.md`. Git, текстовые исходники EPF и контрольный XML отсутствовали. Локально доступны Git, платформа 1С 8.3.27.1936 и файловая база УНФ. Это только локальный toolchain и стенд XML Reader. Целевая среда — УТ Базовая 11.5.24.43 на клиентской платформе 8.3.27.1688. Поэтому проект начинается с воспроизводимого bootstrap, а не с ручного сочинения XML метаданных 1С.

## Этап 0 — подготовка и bootstrap

Статус: начат.

Результат:

- Git-репозиторий и структура каталогов;
- локальная конфигурация путей вне Git;
- штатные команды выгрузки и сборки EPF;
- однократный bootstrap пустой обработки в Конфигураторе;
- первая иерархическая выгрузка EPF в `src`.

Критерий завершения: `src/UpdImport.xml` существует, `scripts/build.ps1` создаёт `dist/ЗагрузкаУПД.epf`, а повторная выгрузка через `scripts/dump.ps1` воспроизводима.

## Этап 1 — XML Reader (первый обязательный milestone)

1. Добавить на управляемую форму асинхронный выбор клиентского XML.
2. Реализовать чтение штатными XML-средствами, доступными в платформе 8.3.27.1688.
3. Проверить корневые узлы и поддерживаемые `ВерсФорм`, `КНД`, `Функция`.
4. Построить нормализованную структуру `Document`, `Seller`, `Buyer`, `Transfer`, `Items`, `Totals`.
5. Без потерь преобразовать даты и числа; сообщения об ошибках сделать предметными.
6. Проверить обязательные поля и контроль `БезНДС + НДС ≈ С НДС` с точностью до копейки.
7. Показать шапку, стороны, валюту, строки и итоги на форме.
8. Определять тестовый режим по наличию необходимых метаданных УТ; создание документа оставить недоступным.
9. Собрать EPF и сверить все контрольные значения с образцом.

Критерий завершения: в УНФ форма показывает документ №230 от 31.03.2026, обе стороны, валюту 643, одну строку и суммы 10380.95 / 519.05 / 10900.00; никаких данных базы не изменяется.

Зависимость: нужен реальный XML `tests/samples/ON_NSCHFDOPPR_6321351636_6324088983_20260618_230.xml`.

## Этап 2 — сопоставление

1. Вынести слой `UTMapper` из парсера.
2. Организацию искать по ИНН продавца, контрагента — по ИНН покупателя.
3. Номенклатуру искать по артикулу/коду поставщика при наличии, затем по точному наименованию.
4. Единицы сопоставлять по ОКЕИ; неоднозначности оставлять пользователю.
5. Показывать статус и ручной выбор в каждой строке.
6. Не создавать отсутствующие справочники.

Критерий завершения: все найденные и ненайденные соответствия объяснимы, пользователь может исправить выбор, парсер не зависит от УТ.

## Этап 3 — адаптер УТ 11.5

1. На тестовой копии УТ Базовая 11.5.24.43 под платформой 8.3.27.1688 исследовать реальные метаданные `РеализацияТоваровУслуг`.
2. Зафиксировать обязательные реквизиты, табличные части и штатный механизм расчёта НДС.
3. Зафиксировать реальные модели организации, партнёра, контрагента, соглашения, склада, цен и НДС; не переносить структуру одноимённых объектов из УНФ.
4. Реализовать `UTDocumentCreator` только по подтверждённым метаданным и API, совместимому с 8.3.27.1688.
5. Проверять дубликат по организации, контрагенту, номеру и дате.
6. Создавать новый документ, заполнять, записывать без проведения и открывать его форму.

Критерий завершения: документ записывается в копии УТ, суммы совпадают с XML, проведение возможно только вручную.

## Этап 4 — безопасная приёмка

1. Повторить контроль XML Reader в УНФ.
2. На копии клиентской УТ загрузить XML и вручную сверить нормализованные данные.
3. Создать и записать реализацию без проведения.
4. Сверить реквизиты, строки, НДС и суммы.
5. После явного решения пользователя провести документ вручную и проверить движения.

## Риски и точки проверки

- Тонкий клиент требует поддерживаемой передачи клиентского файла; API подтверждается на платформе, а не угадывается.
- Реальные метаданные УТ недоступны локально и должны исследоваться на клиентской тестовой копии УТ Базовая 11.5.24.43; метаданные УНФ не являются допустимым источником решений.
- Локальная сборка выполняется платформой 8.3.27.1936, но каждое выбранное API должно существовать в клиентской 8.3.27.1688.
- Контрольный XML пока не добавлен, поэтому приёмка парсера невозможна.
- Двоичные EPF не являются источником истины и игнорируются Git; релизный файл публикуется отдельно как артефакт.
